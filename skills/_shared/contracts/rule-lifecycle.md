# 规则生命周期契约

> 吸收自：a15 The fool ss「Harness 会过期：AI 编程的方法论也在迭代」、a14 孔令飞「规范工具化：46 个 MCP Tool 覆盖全生命周期」、a16 AI实验室「五层闭环架构 + Rules 三层体系」
> 这是新增契约。权威来源在 `../../../docs/` 中无对应单篇，由 18 篇文章综合提炼。

## 核心原则：规则不是静态文档，是会过期的工程资产

> a15 的核心教训：**Harness 是工程资产，不是一次性文档。** 删旧规则同写新规则一样重要——过期的规则不是"无害的冗余"，而是"持续的误导"。

## 规则三层体系（吸收自 a16）

| 层级 | 范围 | 位置 | 变更权限 |
|---|---|---|---|
| User 层 | 个人偏好、个人快捷方式 | `~/.codex/skills/`、个人 MCP 配置 | 个人自由修改 |
| Team 层 | 团队共享规范、编码风格、常用工具 | 本目录 `_shared/contracts/`、WanGo `AGENTS.md` | 团队共识 + Reviewer APPROVE |
| Project 层 | 项目级强制约束、安全边界、交付门禁 | `docs/`、`scripts/` 护栏 | 正式变更控制（BEHAVIORAL 级别） |

## 规则有效期与淘汰机制（吸收自 a15）

每条 Team/Project 层规则应能回答三个问题：
1. **这条规则还生效吗？**——最近一次验证是什么时候、什么场景？
2. **有没有规则因为过时在误导人？**——有没有"历史上用过但现在不生效"的规则？
3. **删规则是否同写规则一样被认真对待？**——有没有因"不敢删"而保留的无用规则？

淘汰检查清单（G10 关闭时执行；v1.8.1 起补齐 docs/32 对照出的删减信号）：
- [ ] 是否有因工具链/宿主/技术栈变更而失效的约束？
- [ ] 是否有从未被真实触发的护栏（死护栏）？
- [ ] 是否有被新的更严格规则覆盖的旧规则？
- [ ] 是否有因"怕删错"而保留但实际已不生效的备用规则？
- [ ] **误伤**：是否有护栏在反例之外拦住了真实合理任务（close 复盘中有记录）？同一护栏误伤 ≥2 次 → 收窄条件或删除，不得只加豁免注释。
- [ ] **无人消费**：是否有规则/文档连续多个 run 的 close 复盘都未被引用、也无任何 run 的证据链触达？
- [ ] **重复实现**：是否有两条规则约束同一件事（漂移风险）？保留更严格或更机器可执行的一条。
- [ ] **模型升级/替换/供应商切换复检**：宿主模型换代或更换供应商后，是否有 Prompt 层提醒已被模型默认能力覆盖、Skill 边界语义漂移、Reviewer 判断口径变化、自动化解析兼容性退化？逐项复检后再继续长任务。

发现过期规则 → 记录 `DECISION`，标记 `deprecated` 或直接删除，不保留。**删减是正常变更**：走与新增相同的提交、版本号与 selftest 更新，不因"只删不加"而免检。

## 任务后能力观察（Add 路径的发现机制，v1.8.1）

> 吸收自 docs/32（腾讯云·蓝翔）：重复路径不该依赖某个人临场提醒才发现。原则：
> **一次问题先修复；重复出现的路径再沉淀；能够机械判断的部分，最后才变成约束。**

Planner 在 close（G10）复盘时做一次轻量能力观察，规则：

1. **只在出现明确信号时输出**：重复劳动、反复纠正、反复找同一上下文、可复用命令、可迁移判断、反复打外部系统、现有规则/Skill/文档缺口、护栏误伤（同时喂给上方 Thin 清单）。
2. **无信号则不输出、不扩建**——不为"以后可能有用"预先建设。
3. 有信号时**只选证据最充分的一条**，说明：事实（本次哪里重复了）、为何会重复、建议载体（文档 / Runbook / Skill / Script / Gate，按下方"脚本实现优先级"渐进）、最小内容、验证方式。
4. **只建议，不自动改**：规则/Skill/文档的写入必须经用户确认后走正常变更控制。
5. 记录位置：该 run 的 `current.md#Change Log` 追加一行（**不新增账本记录类型**，docs/05 的五类之外不加第六类）；被采纳后按载体落位并出现在版本历史。

## 规范工具化（吸收自 a14）

> a14 孔令飞「Harness AI Coding 工程化实践」：**规范工具化**——把 Go 语言全生命周期的规范编码为 46 个 MCP Tool，让 AI 自然遵守。

本工作流对应：
- 能写成 `validate_*.py` 脚本的规则，不要只写在文档里等人看。
- 能挂到 pre-commit hook 的检查，不要只靠 Reviewer 手动发现。
- 文档中的规则描述是给人看的摘要，脚本中的实现是给机器执行的权威版本。

脚本实现优先级：
1. 安全/破坏性操作的硬阻断（已有：`secret_inline`、`unsafe_command`）
2. 结构完整性校验（已有：`validate_workflow.py`、`validate_package.py`、`validate_run.py`）
3. 门禁证据引用的可达性校验
4. 编码风格/命名规范（低优先级，先由 linter 覆盖）

## 护栏分层（吸收自 a16）

| 层次 | 机制 | 何时生效 | 本工作流实现 |
|---|---|---|---|
| Prompt 层 | 自然语言约束 | 模型推理时 | `prompts/` 模板 + SKILL.md description |
| Skill 层 | 角色权限、所有权矩阵 | 角色激活时 | `skills/` 四角色 + `_shared/contracts/` |
| Hook 层 | 提交/推送阻断 | Git 操作时 | `scripts/hooks/pre-commit` + `install_hooks.py` |
| Permission 层 | 沙箱/网络/文件系统限制 | 运行时 | 依赖宿主（Codex sandbox）；团队化时补齐 |

> a16「五层闭环架构」提出的第五层「观测与恢复」在本工作流以 `evidence.md` 只追加账本 + `docs/07-failure-and-recovery.md` 实现。
