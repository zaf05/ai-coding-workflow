## 六问框架：每接入一个 Agent 场景都必须回答（吸收自 Harness Engineering 六支柱）

> atreusliu 原文的核心洞察：**六支柱本质上是六个控制问题**，缺一项未必立刻失败，但会在规模扩大后形成不可见、不可控或不可恢复的断点。这六问可以直接用作**架构评审模板**。

| # | 问题 | 控制维度 | 本工作流对应 |
|---|---|---|---|
| 1 | **看什么？** 信息输入是否完整、可追溯？ | 上下文管理 | Intake（G0）、Recon（G1）、`current.md` |
| 2 | **能触达什么？** 外部工具/系统的能力边界？ | 工具系统 | MCP/Skills（WanGo 层）、scripts/ 确定性校验 |
| 3 | **按什么顺序？** 执行顺序、交接点、门禁？ | 执行编排 | 块 DAG + G0–G10 门禁 + 四角色交接 |
| 4 | **记住什么？** 状态如何持久化、跨会话恢复？ | 状态记忆 | `state.yaml` + `current.md` + `evidence.md` |
| 5 | **如何证明？** 交付证据如何逐条验证？ | 评估观测 | 六层验证框架（L1–L6）+ SHA 绑定 |
| 6 | **如何止损？** 失败如何发现、隔离、恢复？ | 约束恢复 | `docs/07` 失败分类 + `finally` + `max_attempts` + 熔断 |

规则：每次新建工作流或新接入场景时，Planner 必须在 `current.md#Spec` 中逐条回答这六问。任一项未明确回答 → Spec 不通过 G2。

## 风险分层门禁（吸收自 Harness Engineering 批判性校准 #2）

> atreusliu 原文的"先 Spec 后 Code"红线又允许半天内需求直接 Agent 模式——这存在内部冲突。**仅按工时分流会漏掉"小改动、高爆炸半径"任务。**
>
> 批判性校准建议：**改为按风险、可逆性、跨模块影响、数据权限与验收难度分流，不按时间长短分流。**

本工作流对应的风险分流矩阵：

| 维度 | 低风险 | 中风险 | 高风险 |
|---|---|---|---|
| **可逆性** | 单文件、git revert 即可恢复 | 多文件、需手动回滚但不影响其他模块 | 数据库迁移、共享契约修改、不可逆操作 |
| **爆炸半径** | 仅影响一个页面/组件 | 影响多个页面但同一模块 | 跨模块、共享状态、公共组件、API 契约 |
| **数据/权限** | 无数据变更、无权限边界变化 | 新增字段/权限但不影响已有数据 | 数据迁移、权限模型变更、PII 处理 |
| **验收难度** | 单页面、单一视口即可验证 | 多页面、需集成环境验证 | 需跨服务、多租户、真实数据验证 |
| **对应流程** | `FAST`：Mini Spec、紧凑测试、合并审核轮次 | `STANDARD`：完整 Spec→Plan→Implement→Review→Test | `STRICT`：完整门禁 + 额外安全/数据审查 |

**硬规则**：
- 任一维度触及"高风险" → 必须走 `STRICT`，不得降级
- 两维度触及"高风险"或涉及不可逆操作（数据库迁移、共享契约变更、权限模型变更） → 必须额外增加安全审查（G5 前增补 Reviewer 的安全专项 Finding 清单）
- 不得因"改动小"（如只改 5 行但涉及权限检查逻辑）自动降级为 FAST——风险维度优先于文件/行数维度

## Verdict（三值，无第四值）

`APPROVE` / `REQUEST_CHANGES` / `BLOCKED`。不得用"基本批准""有条件通过""大体 OK"。

## 严重度

P0/P1 永远阻塞；P2 除非有权主体明确书面接受否则阻塞；P3 不阻塞转技术债。P0/P1 永不可接受。

## 适用性省略（门禁不递归）

- G0–G4 是 Run/阶段级共享准备，不为每个块重跑。
- G5/G6 面向完整块候选及集成 SHA；G7–G10 面向最终交付。
- 可省略的是"额外审核调用"，不是门禁本身；仍适用的 G2/G3/G4/G5/G8 不能因"任务小"跳过。
- 代码 SHA 改变、真实阻断 Finding、权限/行为/测试预期变化 → 不得沿用失效证据。

## 门禁本身也是规则，规则会过期（吸收自 a15 + Harness Engineering）

> a15「Harness 会过期」+ atreusliu「配置存在 ≠ 行为有效」：**删旧规则同写新规则一样重要。** 过期的规则不是"无害的冗余"，而是"持续的误导"。

本工作流对应：
- 每次 G10 关闭时，Planner 扫描全部门禁定义：是否有因工具链/宿主/技术栈变更而失效的规则。
- 发现过期规则 → 记录 `DECISION`，标记 `deprecated` 或移除，不保留"备用"。
- 不得让"历史上用过但现在不生效"的规则继续留在有效定义中。
- **关键规范必须下沉到 Hook/CI 的确定性执行**，不能只停留在文档承诺层面。能写成 `selftest.sh` 断言的规则，不要只写在 Markdown 里。

## 配置存在 ≠ 行为有效（吸收自 Harness Engineering 批判性校准 #1）

> atreusliu 原文给出了目录、frontmatter、示例和审计项，但**没有证明规则在真实任务中被遵守**。

本工作流对应的强制措施：
- `selftest.sh` 48 项断言——逐条证明护栏真的会开火（不是"写了就会生效"）
- `install_hooks.py` pre-commit——从"有人跑才生效"下沉为"提交即检查"
- 每条关键规范绑定可执行检查：护栏 ID 必须在 `_invalid/` 中有专属反例真实触发
- **死护栏**（有护栏 ID 但无反例能触发）→ `selftest.sh` 报 FAIL，必须补充反例或删除护栏
