### 已确认失败的通道（不要再试）

1. **搜狗返回的跳转链接无法取正文**：搜狗搜索结果的 `href` 指向 `weixin.sogou.com/link?url=...`，解析其 JS 拼接（`url += 'frag1'; url += 'frag2'`）可还原出 `mp.weixin.qq.com/s?src=11&timestamp=...&signature=...` 形式的临时链接，但**该链接抓取返回「参数错误」（响应头 `logicret: -2`）**，正文取不到。搜狗的临时签名链接对 curl 无效。
2. **`mp.weixin.qq.com` 桌面 UA = 软拦截**：返回 HTTP 200 但正文为空壳（仅 17–18 KB，`rich_media_content` 缺失，可见文本 < 100 字）。**必须用移动端 UA 或 MicroMessenger UA**，此时返回 3.4–5.4 MB 完整页面、`js_content` 存在、正文可提取。这是本工作流所有 `mp.weixin.qq.com/s/<id>` 短链核验成功的唯一原因。
3. **`archive.org` / Wayback API 在本环境超时**（40 s 无响应），不能作为兜底镜像通道。
4. **`developers.openai.com` 整个域名对本环境返回 HTTP 403**（桌面 UA / 移动 UA / bingbot UA / googlebot UA 全部 403，`/blog/` 首页同样 403）。这是**出口 IP 被区域封锁**，不是链接失效——见 §五 对该条目的诚实标注。

### a31 · Claude 5 上下文工程新规则：从堆规则到设计信息架构

- **URL**：https://hongtao2agent.xyz/html/claude-5-context-engineering/
- **核验**：2026-09-14 curl HTTP 200，正文全文提取成功（~2800 tokens）
- **标签**：ai coding, harness, context engineering

#### 核心论点

> "We removed over 80% of Claude Code's system prompt … with no measurable loss on our coding evaluations."

上下文过多会成为干扰，而不只是成本。规则彼此重叠或冲突时，模型必须先解释指令体系，再解决用户任务；额外 token 变成决策负担。"怎么写提示词"正在让位于"信息放哪一层"。

#### 七个关键判断（完整版）

**01 · Compilation（编译）**

Prompt 只是入口，模型真正看到的是"编译后上下文"。单条用户消息只占输入的一小部分；system prompt、Skills、CLAUDE.md、memory 和其他来源会共同构成模型实际接收的上下文。因此结果不佳时，不能只改最后一句 prompt，还要检查整条上下文装配链。

- **AIWorflow 吸收**：三层模型已区分 Flow/Role/Evidence 上下文来源
- **调试视角**：应像排查编译产物一样排查最终上下文：来源、优先级、重复、冲突和何时加载

**02 · Subtraction（减法）**

先进模型的上下文优化，首先是一道删除题。Claude 5 团队删除了 Claude Code system prompt 的 80% 以上，编码评测没有可测损失。关键不是节省 token，而是移除旧模型时代积累的防御性约束与指令冲突。

同类请求可能同时出现"适当补文档"和"不要加注释"等冲突信息。新模型更能利用周围代码和用户意图作判断；memory、artifacts 与 skills 接管了 CLAUDE.md 过去混合承担的职责。

- **AIWorflow 吸收**：应审查所有 SKILL.md 是否有"旧模型时代积累的防御性约束"可删除
- **指标边界**："无可测损失"仅指文中提到的编码评测，不等于所有仓库、治理与长尾安全场景均无损

**03 · Judgement（判断替代规则）**

把情境性偏好写成绝对规则，会让正确答案变成违规答案。旧指导一刀切限制注释和文档；新指导要求代码匹配周围项目的注释密度、命名和习惯。这不是取消标准，而是把标准从"固定动作"改为基于局部证据的适配原则。

- **写法升级**：高质量上下文更像判定原则与证据来源，而不是覆盖所有分支的动作清单
- **硬约束仍在**：安全、合规、权限和不可逆操作不能只依赖模型判断

**04 · Interfaces（接口设计替代示例教学）**

示例会暗中缩小搜索空间，接口本身应表达行为契约。旧做法用示例教模型如何调用工具；新做法更重视参数是否有表达力、状态是否有明确枚举、约束能否直接编码。接口设计的目标，是让合法动作空间自解释，而不是让模型照抄一条演示路径。

- **工程转移**：提示工程的一部分正在变成 API 设计——类型、枚举、必填字段与错误返回比长篇教学更稳定
- **不是禁用示例**：当语义含糊、格式脆弱或边界案例重要时，少量反例和验收样例仍可能有价值

**05 · Loading（渐进披露替代全量加载）**

常驻上下文应只保留路由信息，专项知识按需加载。代码审查、验证等详细规则从 system prompt 移入可选择调用的 Skills；部分工具定义通过 ToolSearch 延迟加载。CLAUDE.md 和 Skill.md 也应形成树状结构：顶层告诉模型去哪里找，而不是把所有内容提前塞入。

- **Skills**：专项流程在任务匹配时加载
- **Tools**：大量低频工具先隐藏完整 schema，通过搜索发现
- **Files**：CLAUDE.md 与 Skill.md 指向细分文件树，而非成为中央百科全书
- **失败模式**：路由名称含糊、触发条件太弱或层级过深，会让模型根本找不到已拆分的信息

**06 · Ownership（职责归位替代重复说明）**

重复说明和手工记忆正在被"职责归位"替代。工具用法只放工具描述，不再同时复制进 system prompt；与个人和工作有关的长期事实交给 auto-memory，而不是不断写进 CLAUDE.md。同一事实只保留一个权威位置，能减少版本漂移与冲突优先级。

- **知识治理**：这是一种 Single Source of Truth——信息与最接近其生命周期的组件绑定
- **记忆风险**：文章没有展开 auto-memory 的删除、过期、纠错、敏感信息与团队共享边界

**07 · References（富引用替代简单规格）**

最好的规格正在从"描述目标"变成"展示可验证对象"。新模型可以读取 HTML artifact、测试套件、其他代码库中的实现与 rubric，而不只依赖简化 Markdown plan。引用越接近最终产物的表示形式，模型越容易获得高保真约束与可验证标准。

- **描述型规格**：说明想要什么，但可能丢失结构与细节
- **实现型引用**：代码、测试和 mockup 直接暴露结构、行为与边界
- **评价型引用**：rubric 把模糊的质量偏好转换为可检查维度
- **引用不等于真相**：旧代码、脆弱测试和错误 mockup 会高保真地传播错误

#### 旧规则 → 新规则对照表

| 维度 | Then（旧模型时代） | Now（Claude 5 时代） | 真正变化 |
|---|---|---|---|
| 行为控制 | 写大量绝对规则，预防最坏情况 | 给出原则，让模型结合局部情境判断 | 从动作清单转向判定标准 |
| 工具教学 | 用示例演示固定调用方式 | 用参数、枚举与不变量设计接口 | 从模仿路径转向合法空间 |
| 知识加载 | 关键说明全部放在 system prompt | Skills、文件树和 deferred tools 按需加载 | 从常驻全文转向索引与路由 |
| 工具说明 | 同一规则写进多处 | 由工具描述拥有 | 从跨层复制转向本地所有权 |
| 规格形式 | Markdown plan | HTML artifact/测试套件/rubric | 从抽象描述转向可验证对象 |

### a32 · DeepSeek Harness 插件机制全景解读

- **URL**：https://hongtao2agent.xyz/html/deepseek-harness-plugin-architecture/
- **核验**：2026-09-14 curl HTTP 200，正文全文提取成功（~2900 tokens）
- **标签**：ai coding, harness, plugin architecture

#### 核心判断

> "DeepSeek Harness 最强的不是『插件更多』，而是把 Agent 运行时的差异变成有作用域、有依赖、有生命周期、有日志的组合结构。"

这不是一套狭义的插件 API。DSH 用 Cordis 管理 Context、Service、Fiber、Event 与 Effect；用 Profile/Bundle/Patch 装出整个进程；用 Preset/Scope 决定某类 Agent 看见的工具和提示词；再用追加式 Session Log 与统一 Tool Pipeline 保证执行可恢复、可拦截、可审计。官方仍将项目标记为 Developer Preview。

#### 五层插件原理（完整版）

**01 · Assembly（装配层）：Profile 装出进程，Preset 装出 Agent**

Bundle 分发插件配置层，Profile 选择一组 Bundle，Patch 按顺序覆盖；Preset 则在进程内部建立某类 Agent 的局部能力视图。前者回答"宿主有什么"，后者回答"这个 Agent 看见什么"。

- 配置顺序：Bundles → Profile Patch → Home Patch → CLI Patch
- Preset：每个 generation 形成 standing composition，Session 通过 scope parent 加入
- 解析：agent → preset → global，近层注册遮蔽远层
- **AIWorflow 对应**：Flow 层 DAG（进程装配）vs Role 层所有权（Agent 可见范围）
- **边界**：共享 standing instance 要求有状态插件按 Session/Agent 分键；非 blank Session 不能切换 Preset

**02 · Runtime（运行时层）：Context 是服务总线，Fiber 是生命周期单位**

插件通过 `ctx.<service>` 访问能力，以 inject 声明依赖；每次挂载产生一个 Fiber，管理插件状态、子插件、注册项与释放动作。

- 生命周期状态机：PENDING（依赖缺失）→ LOADING → ACTIVE → UNLOADING → DISPOSED；异常进入 FAILED
- Provider 消失会使 Consumer 卸载；Provider 恢复后可重新加载
- 加载顺序从人工编排变成依赖图问题，Provider 替换不必重写消费者
- **边界**：PENDING 可能是合法等待，也可能是漏配依赖

**03 · Effects（效应层）：Effect 把"注册"与"撤销"放在一起**

工具、事件监听、Service、Timer、Watcher 等资源绑定到当前 Fiber；插件卸载、依赖变化或 HMR 时，运行时调用 disposer 并递归清理子树。

- disposer 按注册逆序开始执行（不保证严格串行 LIFO）
- 有关联的清理应放进同一个 disposer 顺序 await
- **AIWorflow 对应**：`finally` 块 + 熔断
- **边界**：Effect 不是外部事务——已发送消息、网络请求或数据库写入不会自动回滚

**04 · Agent Loop（循环层）：固定循环骨架，开放事件与能力扩展点**

Agent Loop 组装 Prompt 与 Tool Schema、调用 LLM、接收 Assistant Message、执行工具并继续下一 Step。请求、流式响应和工具执行暴露为 Event/Waterfall。模型可见信息必须能从追加式 Session Log 重建。

- 一次 Turn：记录用户消息 → 派生 Prompt → agent/pre-step → request → llm/stream → assistant/message → tool/call → 统一工具流水线 → tool/result
- 恢复、Fork、Trajectory 与 UI 投影围绕同一事实日志工作
- **边界**：可重建不等于外部世界确定；网络、时间、文件和模型 Endpoint 仍会带来噪声

**05 · Capabilities（能力层）：Capability Seam 让 Provider 可整体替换**

Filesystem、Subprocess、Sandbox、Session Storage、LLM 等能力拆成 Definition、Provider 与 Consumer；工具依赖稳定接口，部署选择本地、远程或受控 Provider。

- Definition：定义稳定 Service 契约
- Provider：实现本地、沙箱或远端能力
- Consumer：Tool 与 Loop 只消费接口，不绑定部署位置
- 可把本地 Bash/FS 换成远程 Workspace，上层 Tool 和 Agent Loop 不变
- **边界**：接口可替换不代表语义完全一致；延迟、隔离强度和功能子集仍需部署验收

#### 三条代码路径

| 维度 | 普通 Cordis Plugin | Dynamic Cordis Package | PTC / Code Mode |
|---|---|---|---|
| 入口 | npm、本地或仓库插件 | cordis_inspect/define/run/stop | run_code |
| 运行位置 | DSH Host 主进程 | Host half: node:vm; Browser half: 页面 Runner | Fresh Node Worker |
| 生命周期 | 由 Profile/Preset 配置长期加载 | 仅进程内存；重启丢失 | 每次 run 新建，完成后销毁 |
| 信任边界 | 可信同进程代码 | node:vm 只隔离 globals | Worker 是 containment |
| 最适合 | 长期产品能力 | 快速验证运行时扩展 | 减少多步工具往返 |

#### 统一工具执行流水线

1. **Durable**：tool/call 记账——在执行前记录
2. **Policy**：pre-execute——Hook、权限与策略开始介入
3. **Gate**：Guard + 审批——只能单调收紧
4. **Dispatch**：tools/execute——包裹超时、重试、指标并调用 Tool Body
5. **Result**：post → result——规范化权威结果，持久化 tool/result

#### Plugin、Tool、Skill、MCP 的层次关系

| 概念 | 定义 |
|---|---|
| **Plugin** | 运行时组件。可以提供 Service、Tool、Hook、Prompt、UI、Agent Loop 或 Provider |
| **Tool** | 模型可调用的一个函数。由插件注册，Schema 给模型，执行回调留在 Host |
| **Skill** | 按需加载的说明书或工作流，主要进入 Prompt；指导模型如何组合工具 |
| **MCP** | 外部工具协议。MCP Client 自身是 Cordis 插件，把 Server Tools 桥接到统一 Tool Registry |

#### 工程边界（Developer Preview 限制）

- API、文档与源码可能快速漂移
- 不是一插件一沙箱：普通 Plugin、用户 Preset 与 MCP Server 都需要高信任
- isolate ≠ 安全隔离：处理 Service realm 与可见性，不阻止恶意 Node 代码
- Effect ≠ 事务：外部消息、网络请求、数据库写入仍需幂等与补偿
- 上下文不会自动变小：能力越多，Prompt、Skill 与 Tool Schema 固定成本越高

#### 最值得吸收的设计

1. **Preset/Scope 的分离**：决定某类 Agent 看见什么，比决定"装了什么"更重要
2. **插件的价值常来自收窄**：通过 Preset 删除无关工具，降低选择歧义
3. **统一工具执行流水线**：审批、权限、超时、重试、遥测不侵入业务 Tool
4. **Session Log 作为单一事实源**：模型可见输入与工具结果进入持久 SessionEvent

### a33 · Agentic SRE：重写可靠性控制面

- **URL**：https://hongtao2agent.xyz/html/agentic-sre-control-plane/
- **核验**：2026-09-14 curl HTTP 200，正文全文提取成功（~2500 tokens）
- **标签**：agent, sre
- **来源**：Neel Shah / DZone, "A Practical Architecture"

#### 核心论点

> "A reliable agent is not one that knows everything. It is one that acts only within well-defined limits and remains observable, reversible, and accountable."

Agentic SRE 的核心产品不是"聪明诊断"，而是受治理的行动能力。传统自动化把预先写好的规则映射到固定动作；Agentic SRE 则能根据上下文选择路径、跨工具编排步骤，并在权限边界内采取行动。

- **价值公式**：更快聚合上下文 + 更少重复操作 + 更一致的初步响应
- **安全公式**：最小权限 + 动作分级 + 人工 Gate + 可回滚 + 全链路审计
- **组织公式**：SRE 从亲手操作转向设计策略、运行 Playbook、监督 Agent 与改进可靠性系统

#### 八层论证（完整版）

**01 · Definition（定义）：受限自主，不是聊天助手也不是无人值守**

Agent 可以采集遥测、关联信号、提出原因、调用工具，并在超出权限时交还人类。与规则自动化相比，它能根据上下文选择多条路径。真正变化的是适用边界与决策自由度，不是"有没有 AI 建议"。

- 输入：遥测、部署历史、Runbook 与服务状态
- Agent 能力：总结、关联、诊断、建议、低风险执行
- 关键差异：根据上下文选择路径并跨工具编排，而非固定的 if X then Y
- 退出条件：问题超出授权时转交人类
- **本质**：Agentic SRE 的核心不是语言界面，而是"在生产环境里被授予多少判断和行动权"

**02 · Need（需求）：第一瓶颈往往不是修复，而是把碎片拼成情境**

告警噪声、碎片化可观测数据、持续部署和动态基础设施，让工程师在真正诊断前耗费大量时间收集上下文。Agent 最现实的价值，是压缩"检测到理解"之间的路径。

- 环境压力：告警风暴、遥测割裂、持续部署、基础设施动态变化
- 第一公里：过滤重复告警、补充部署历史、从日志提取模式、寻找 Runbook
- 重复任务：开工单、通知 Owner、检查健康状态、验证回滚安全性
- **价值单位**：Agent 不必一次给出正确根因；只要显著降低搜索、切换工具和重复核对的成本
- **数据前提**：如果遥测缺少 join key、时间同步、服务拓扑和变更记录，Agent 只会更快生成一个连贯但断裂的故事

**03 · Human（人类角色）：从操作者上移为策略作者、系统设计者和可靠性监督者**

Agent 擅长模式识别、总结和边界内执行；人类仍负责权衡、风险评估、组织上下文，以及决定什么时候不行动。可靠性不仅是技术问题，也是业务与协调问题。

- Agent 优势：模式、速度、总结、受限执行
- 人类优势：权衡、风险、业务语境、跨团队协调、克制不行动
- 治理职责：定义政策、Guardrail、升级阈值和不可委托动作
- 角色变化：Operator → System Designer → Policy Author → Reliability Supervisor
- **自动化偏误**："保留人工确认"并不自动保证监督有效；审批界面必须展示证据、差异和风险

**04 · Entry（入口）：最优入口是低风险、高频、易评估**

事故摘要、告警增强、日志关联、Runbook 检索、变更影响分析和复盘初稿，都能在不直接修改生产状态时创造价值。自动执行只应出现在预批准、低风险、可回滚的场景。

- 只读价值：摘要、告警增强、日志关联、Runbook 和知识库检索
- 事故协作：聚合时间线、检查近期变更、减少重复劳动
- 修复建议：扩容、重启任务、关闭错误 Feature Flag、回滚部署
- **选择原则**：频率高、输入可得、输出可验、失败可控、价值可量化

**05 · Architecture（五层架构）**

模型只是推理层，可靠性来自外围控制系统。有效系统需要五层共同工作：

| 层 | 职责 | AIWorflow 对应 |
|---|---|---|
| Telemetry | Metrics、Logs、Traces、Events、Deployment data | Evidence 账本 + SHA 绑定 |
| Reasoning | 解释上下文并选择下一步（通常 LLM 驱动） | Planner 决策 |
| Tools | 查询 Dashboard、读取配置、开工单、触发 Runbook | Implementer 工具能力 |
| Policy | 权限、审批、速率限制、失败边界 | G0–G10 门禁链 |
| Audit | 追踪每个决定、建议和动作 | ledger 轮次日志 |

**06 · Trust（分层信任）**

信任不是主观感受，而是权限、分级、回滚和证据共同产生的结果。团队既不能盲目信任，也不能永久怀疑。

- Permission scoping：权限窄、明确、绑定具体任务
- Action tiers：低风险自动、中风险确认、高风险仅人类
- Rollback：自动动作必须能快速反转
- Agent observability：记录观察、推断、建议、动作和结果
- **回滚不总可用**：数据删除、流量丢失、级联通知和外部系统调用可能不可逆

**07 · Operating Model（运行模式）**

Runbook 从压力下阅读的文档，变成机器可执行的操作契约。Agent 在人类加入前完成初步收集与分诊；Runbook 需要明确前置条件、决策点和行动边界；事故后由 Agent 收集证据与草拟时间线。

- **契约化**：机器可读 Playbook 的真正价值，是把隐性的判断条件、执行权限和失败出口变成可测试接口
- **知识损失**：过度结构化可能遗漏专家在异常场景中的隐性适应

**08 · Failure & Rollout（失败模式与上线顺序）**

失败模式决定上线顺序：先窄、先读、先测，再逐步扩大权限（Progressive Autonomy）。

### a34 · Pi 的 Compaction：长会话如何继续工作

- **URL**：https://hongtao2agent.xyz/html/pi-compaction/
- **核验**：2026-09-14 curl HTTP 200，正文全文提取成功（~2600 tokens）
- **标签**：ai coding, context management

#### 核心论点

> "Compaction replaces part of the history with a compressed representation, leaving room for additional messages and tool calls."

文章回答了一个很工程化的问题：coding agent 在长时间执行任务时，如何在有限上下文中保持连续性。从一次 LLM 请求的组成讲起，解释会话为何会膨胀，随后拆解 Pi 的触发时机、保留窗口、专用摘要请求、session 写回方式与 prompt caching 代价。

#### 六层机制（完整版）

**01 · STATE（状态）：上下文不是聊天记录，而是 Agent 的临时执行状态**

每次 LLM 调用都要带上 system prompt、工具、加载文件和会话历史。模型没有天然延续的内部工作现场，连续性来自 Agent 重建输入。因此工具输出、代码片段和反复解释都会占用同一个有限预算。

- 前提：LLM 有有限 context window
- 机制：每次请求包含先前消息与工具调用结果
- 结果：会话长度持续单调增长，最终请求被拒绝
- **为什么重要**：Agent 的"记忆"首先是一种输入编排，而不是模型内部永久状态
- **边界**：文章没有展开 system、tools 与文件各自占多少 token

**02 · CHOICE（选择）：溢出不是单纯容量问题，而是连续性策略选择**

达到上限时可以开一个空会话，也可以保留较小的历史表示。前者清爽但失忆，后者延续工作但引入有损压缩。文章还提醒：更长的上下文并不必然更好，context rot 使"重启"在某些场景也合理。

- 空会话：释放全部历史预算
- 压缩：以摘要替换部分历史
- 补充条件：上下文变长时，模型输出质量也可能下降
- **为什么重要**：正确问题不是"能否塞进窗口"，而是"下一步工作真正需要哪些状态"

**03 · TRIGGER（触发）：Pi 优先在轮次结束后压缩，并为中途溢出保留兜底**

自动检查放在 turn 结束后，可以让当前轮的请求继续复用同一缓存前缀。若中途真正收到 overflow error，Pi 仍可能 mid-turn compact。用户也可用 `/compact` 主动触发。

- 正常入口：turn 结束后检查阈值
- 人工入口：执行 /compact
- 异常入口：mid-turn 遇到 context overflow
- **为什么重要**：选择 turn boundary 是一致性与成本的折中
- **边界**：原文没有公开阈值公式，也未说明 mid-turn 压缩后如何恢复

**04 · SPLIT（切分）：截断点由 token 预算决定**

Pi 默认原样保留约 2 万 tokens 的近期消息，文章估算约为 5–20 轮。更早的消息被提取、序列化并送去摘要。这里保留的是 token 预算，不是固定消息数，所以长工具输出会显著改变被保留的轮数。

- 不变部分：近期消息按原样保留
- 变化部分：旧轮次由摘要替代
- 决定因素：token budget，而非固定 turn count
- **为什么重要**：近期窗口相当于工作内存——代码 diff、最新错误与未完成工具链比很早的探索过程更需要逐字保真
- **边界**："近期"不等于"重要"。关键约束若很早出现但未进入摘要，仍可能丢失

**05 · SUMMARIZE（摘要）：摘要请求像换班交接，而不是继续解决原任务**

Pi 为 compaction 使用专门的 system prompt 和 user prompt，目标是提取仍然影响下一步的目标、进展与关键决策。这条请求不带原 conversation history，可独立选择模型；结果以纯文本 compaction entry 写入 session。

- 输入：截断点之前被序列化的旧消息
- 任务：保留下一次请求仍有用的信息
- 输出：plain-text compaction entry
- 结果：新 prompt 由 summary 与近期消息共同组成
- **为什么重要**：摘要格式其实是 Agent 的状态接口——它决定下一任模型能看到哪些事实、决策和待办
- **边界**：文章描述了摘要结构，但没有提供摘要质量评测、事实一致性检查或遗漏恢复机制

**06 · CACHE（缓存）：压缩会重写 prompt 前缀，必须支付一次缓存失效成本**

Prompt caching 依赖 exact prefix match。summary 替换 older history 后，哪怕近期消息的 token 没变，它们所处的前缀也变了，旧缓存无法沿用。不过之后的请求会围绕新前缀继续增长，缓存可以重新建立。

- **为什么重要**：Compaction 不是免费优化——它在 token 容量、推理质量和缓存成本之间重新分配预算
- **边界**：原文没有给出具体 provider 的缓存价格、命中率或压缩前后的成本实测

#### 运行流程

```
Phase 01 完整会话增长 → Phase 02 触发检查 → Phase 03 切分历史
→ Phase 04 独立摘要 → Phase 05 写回并继续
```

新上下文 = system + tools + summary + recent turns + 新消息

#### 与 AIWorflow 的关系

Pi Compaction 和 AIWorflow 的"中断恢复"（ledger 轮次日志 + state.yaml）解决同一个问题：长会话上下文溢出与状态丢失。Pi 走运行时压缩路线，AIWorflow 走持久化状态恢复路线——两者互补。
