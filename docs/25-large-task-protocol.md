# 25 · 大型任务拆分与跨 Run 交接协议

> 适用场景：一个需求需要拆成多个 Run（跨天/跨模块/跨角色）才能完成。
> 核心问题：Run 2 怎么不重复 Run 1 已经完成的理解工作。

## 一、什么时候必须拆

| 信号 | 阈值 |
|---|---|
| 变更文件数预计 | > 15 个 |
| 预计代码行数 | > 1,500 行 |
| 涉及模块数 | ≥ 3 个（前端+后端+DB 等） |
| 单个 Run 上下文 | 接近压缩阈值 |

超过任一阈值，Planner 必须在 G2 Spec 阶段拆分为多个子 Run。

## 二、拆分原则

1. **纵向优先**：每个子 Run 完成一个可验证的用户可见功能切片，不按技术层横切。
2. **文件所有权不重叠**：两个并行子 Run 不得修改同一个文件（否则串行）。
3. **接口先行**：如果子 Run 之间有依赖，先跑"接口定义 Run"，再跑实现 Run。
4. **每个子 Run 独立可验收**：合入集成分支后可独立通过 G6/G7。

## 三、跨 Run 交接（核心机制）

### 交接载体：context/ 目录

```
Run 1 完成时（G10）写入：
  context/project-<项目>.md       ← 项目画像更新
  context/area-<模块>.md          ← 本模块已知问题/测试缺口
  context/decisions.md            ← 本次做出的架构决策
  context/risk-register.md        ← 本次踩到的坑

Run 2 启动时（G1）读取：
  匹配的项目画像 + 模块画像 + 决策记录 + 风险登记
  → 不再从零理解项目
```

### 交接信息（Run 1 → Run 2）

| 信息 | 载体 | Run 2 怎么用 |
|---|---|---|
| 项目架构/关键文件 | `context/project-*.md` | G1 直接获得项目画像，跳过全库扫描 |
| 已完成的模块/决策 | `context/decisions.md` | G2 Spec 不重新讨论已定方案 |
| 已知风险/检查规则 | `context/risk-register.md` | G4 TestPlan 直接纳入已有风险 |
| 测试缺口 | `context/area-*.md` | G4 优先补上 Run 1 遗留缺口 |
| 接口契约 | `contracts/` 目录 | G2 直接引用，不重新定义 |

### 交接检查清单（Run 1 的 G10 必须逐条确认）

- [ ] 项目画像已更新（或确认无需更新）
- [ ] 架构决策已记录（如有新决策）
- [ ] 风险已登记（如有新发现）
- [ ] 测试缺口已记录（如有遗留）
- [ ] 接口契约已导出（如涉及跨模块接口）
- [ ] 下一个 Run 的输入已明确（哪些文件/契约/决策）

## 四、Run 2 的 G1 增强行为

有历史 context 时，Run 2 的 Recon 阶段执行：

1. **读 context**：加载匹配的项目画像/模块画像/决策/风险。
2. **增量扫描**：只扫描 Run 1 之后变更的文件（`git log <run1_end_sha>..HEAD`），不重新全库扫描。
3. **继承理解**：Run 1 已标注"已理解"的文件，Run 2 只看 diff，不重读全文件。
4. **验证时效**：context 中的知识如果对应的 SHA 已不在当前分支，标记过时并重新验证。

## 五、与 Blast Radius 配合

大型任务的 Run 2 在 G5 前执行影响面范围（C1）时：
- 读取 `context/area-*.md` 中记录的依赖关系，扩展影响面清单
- 不再从零构建依赖图（Run 1 已记录的依赖直接复用）

## 六、度量（个人用，无看板）

每个 Run 的 `state.yaml` 增加时间戳记录：

```yaml
timestamps:
  g0_intake: "2026-09-17T10:00:00+08:00"
  g1_recon: "2026-09-17T10:05:00+08:00"
  g2_spec: "2026-09-17T10:20:00+08:00"
  g3_user_approve: "2026-09-17T10:30:00+08:00"
  g4_test_plan: "2026-09-17T10:35:00+08:00"
  g5_implement: "2026-09-17T11:00:00+08:00"
  g6_integration: "2026-09-17T11:15:00+08:00"
  g7_full_verify: "2026-09-17T11:30:00+08:00"
  g8_release: "2026-09-17T11:35:00+08:00"
  g9_post_merge: "2026-09-17T11:40:00+08:00"
  g10_close: "2026-09-17T11:45:00+08:00"
```

从 timestamps 可计算：
- 总耗时：`g10_close - g0_intake`
- 各阶段耗时：相邻时间戳差
- 人工等待时间：`g3_user_approve - g2_spec`（用户审批耗时）
- 实际工作时间：总耗时 - 人工等待时间
