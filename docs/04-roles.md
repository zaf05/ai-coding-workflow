# 04 · 角色与所有权

## 所有权矩阵

| 活动 / 产物 | Planner | Implementer | Reviewer | Tester |
|---|---|---|---|---|
| 需求接收、Spec、块 DAG、变更预算 | 负责 | 读取 | 审核 | 读取 |
| 仓库画像与接管评估 | 负责 | 读取 | 必要时审核 | 贡献测试基线 |
| `state.yaml` 与缺陷归因 | **唯一写入者** | 读取 | 读取 | 读取 |
| `current.md` 正文 | 负责 | 读取 | 只读审核 | 读取 |
| `test-plan.md` | 协调 | 读取 | 审核计划 | **负责** |
| `evidence.md` 账本 | 原样串行追加 | 提交实现报告 | 提交审核载荷 | 提交测试/缺陷载荷 |
| 审核结论与 Finding | 读取并引用 | 读取 | **唯一作者** | 读取 |
| 生产代码实现 | 禁止 | **每次一个块** | 禁止修改 | 禁止修改 |
| 块级单元/组件测试 | 禁止 | 负责 | 读取 | 审核 |
| 集成与目标分支合并 | 负责（授权内） | **绝不合并** | 发布门禁 | 验证合并后 SHA |

**路由说明**：四个角色的 `SKILL.md` description 是宿主路由边界，按"触发条件 / 不触发条件 / 不做什么"编写，不写营销词。被错误触发的角色应先返回精确缺口，而不是强行兼任。

## 职责分离（硬规则）

1. 任何角色不得批准自己创建或修改的产物。
2. Planner 不得编写或修复生产代码，也不得修复合并冲突中的代码。
3. Reviewer 对被审对象只读，只能发布新的审核产物。
4. Tester 可以修改测试代码与测试产物，但不得修改生产代码、已批准行为，也不得仅为通过而改断言。
5. Implementer 每次只处理一个已批准块/Task，或一个归因为 `IMPLEMENTATION` 的 Defect。
6. 同一 Run 在任一时刻只能有一个 Planner 写全局状态。
7. 请求跨越角色边界时，向负责的 Planner（独立调用时向调用者）返回**精确缺口**，必要时 `BLOCKED`；不得悄悄兼任角色或自行委派另一个角色。

## 单活跃角色与串行推进（设计边界）

frontier 可以同时出现多个 ready 块，但 `run_flow.py --advance` 每轮只推进 `ready[0]`，且同一 run 的 `state.yaml` 只有 Planner 一个写入者。这是治理设计，不是调度能力缺口：串行推进让门禁、证据和状态迁移保持可审计，避免多个角色同时改写全局状态。

并行发生在 **工作包层**：多个 run / 多个 worktree 可以按主仓交付协议并行，受文件所有权和集成顺序约束；并行不发生在单个 run 内部。若未来确实需要 run 内并行，必须先登记新的 F 项评估写入者、门禁合并语义和副作用隔离，不允许默认打开。

## 单层调度，不递归研发

- 只有当前 Run 的 Planner 可以创建正式 Task/块并直接调度角色；不为每个块再启动 Planner。
- Reviewer / Tester / Implementer 只完成交接动作：不创建子 Run/Task、不重规划 DAG、不再派生角色链（包括通过命令行绕行）。
- Implementer 可以在一个块内维护步骤、检查点、分步实现与自测；这些不是新的审批对象。
- Tester 把用例分组、Reviewer 按维度检查，也不能把内部步骤升级成子任务。
- 角色完成或遇到职责外问题后交回同一 Planner；会话恢复不创建新的任务层级。

"调度"指**决策所有权**，不是必须嵌套工具调用。宿主主会话只负责转发与原样回传，不是第二个 Planner，也没有规划、状态或证据写入权。

## 交接身份（每次委派必须给全）

缺少下列任一项，接收角色应当 `BLOCKED` 而不是猜测：

- Run ID 与块 `label`；单一角色动作（做什么，不做什么）
- 产物路径与对象修订；相关 Spec/计划版本
- 精确 `base_commit` / `head_sha` / `tested_sha`（完整 SHA，不是分支名）
- 适用的 Finding / Defect ID
- 允许写入路径与受保护路径
- 预期输出契约（用哪个模板、写到哪）
- 停止条件与预算（token/时间/轮次、熔断阈值）

完整材料通过持久路径与不可变身份引用，不重复粘贴，也不依赖完整对话历史。"审核一下""完成它"这类请求不充分。

## 会话与熔断

- 一个实现会话只处理一个工作包/块，使用最小任务包（约 3,000 token：目标、基线、接口、路径、验收、停止条件）。
- **5 分钟无可观察产物即中断**；**30 分钟软检查点**汇报进度与缺口。
- 轮次耗尽、上下文超限、解析失败**不自动恢复累计会话**；同一 Finding 第二次失败时改用全新会话 + 最小根因包。
- 实现、返修、Reviewer、Review Runner 会话统一执行上述熔断。

## 复核者数量

- `STANDARD` / `HIGH_RISK` 默认**一名**主独立复核者。
- 第二名只用于：用户明确要求，或主复核者发现需要不同专业判断的 blocking 安全/架构问题。
- Advisory 级意见默认转后续技术债，不进入返修循环。
- 一轮 Findings 默认由**一个**修复会话统一处理；超出任务包规模时才按共享根因拆最少批次。

## 跨宿主交叉复核（双宿主调度偏好）

- 双宿主（Codex / Claude Code）同时可用时，CODE_REVIEW / RELEASE_REVIEW 等审核类工作**优先由非实现宿主的会话执行**：候选提交的 Implementer 宿主与 Reviewer 宿主不同，降低同源上下文偏差与「自己写、自己过」的风险。
- 来源：flow-next「adversarial cross-model reviews」（附录 029，`docs/21` §a29）+ 2026-09-25 四问题对账确认——v1.8.18–v1.8.20 三个版本的候选提交事实上均经另一宿主逐行复核后才推 main，本节把该既有实践成文为规则，不是新增能力。
- 这是**调度偏好不是硬门禁**：单宿主环境退化为「Reviewer 必须是独立只读会话」，不阻塞流程；引擎不校验宿主归属，可由 ledger 的 owner/model 字段事后审计。
- 不放宽既有边界：即使跨宿主，「任何角色不得批准自己创建或修改的产物」、Verdict 绑定 SHA/命令输出等规则全部照常生效。

## 影响面范围（Blast Radius）

> 依据：`23-reference-scan-20260916.md` C1/C4（来源 a2 code-review-graph + r4 context-mode）。

Reviewer 和 Tester 在开始审查/测试前，必须先获得或自行产出一份**确定性影响面文件清单**，不得默认全库扫描：

1. **产出方式**（按优先级）：
   - Planner 在 Spec/块定义中已标注允许路径 → 直接使用；
   - 否则由执行角色运行 `git diff --name-only <base>...<head>` 获取变更文件列表；
   - 对每个变更文件，按目录归属和调用关系（`grep -r` 搜索符号引用）扩展到受影响的邻接文件。
2. **使用方式**：
   - Reviewer 只审查清单内文件 + 变更 diff，不阅读清单外的实现代码；
   - Tester 优先在清单内文件对应的测试和邻接回归中选取用例，不全量重跑。
3. **边界**：影响面范围是**效率约束**，不是正确性豁免。若审查/测试过程中发现影响超出清单，必须回报 Planner 扩大范围并更新清单，不得静默截断。
4. **最小任务包配合**：传给 Reviewer/Tester 的材料应包含已执行的确定性命令输出（diff 统计、影响面清单），而非要求 Agent 重新从零读取原始文件。
